# Оценка синхронизации с БД (Firestore)

## Текущая архитектура

```
Firestore (коллекция plan_state, документы shared_<key>)
    ↑ подписка onSnapshot
SyncContext: remoteSnapshot, pendingUpdates, persistStateKey, pushLocalToCloud
    ↑ применяет снапшот
usePlanState: состояние приложения (savedPlans, manualAssignments, …)
    → при изменениях вызывает persistStateKey(key, value)
remoteStorage: очередь updateQueue, debounce 400ms → flushQueue
    → читает коллекцию, сравнивает rev, пишет только изменившиеся ключи
```

**Плюсы:**
- Подписка на коллекцию даёт актуальные данные при изменениях с других вкладок/устройств.
- Debounce 400ms уменьшает количество записей при частых действиях.
- Ревизии (rev) не дают перезаписать более новое значение из облака.
- Проверка по содержимому (lastKnownValueContent) снижает лишние записи и петли.
- При ошибке записи вызывается flushErrorCallback (откат части состояния, уведомление).

**Что можно улучшить**

### 1. Надёжность
- **Запись по ключам последовательная** — в `flushQueue` цикл `for...await` пишет документы по одному. При 5–10 ключах задержка растёт. **Решение:** писать ключи параллельно (`Promise.all`), с лимитом одновременных запросов при необходимости.
- **Нет повтора при сбое** — одна неудачная запись сразу вызывает flushErrorCallback. Временные сетевые сбои лучше обрабатывать 1–2 повторами с небольшой задержкой.
- **Очередь только в памяти** — при перезагрузке страницы во время sync несохранённые изменения в `updateQueue` теряются. Для критичных сценариев можно дублировать очередь в localStorage/IndexedDB и восстанавливать при старте.

### 2. Упрощение
- **Два источника правды о pending** — `pendingUpdates` в React state (SyncContext) и `pendingUpdatesRef`. Ref нужен в applyRemoteSnapshot и flushQueue, state — для ре-рендеров. Можно оставить только ref и триггерить обновление UI по версии/флагу, чтобы не дублировать большой объект в state.
- **Много ключей в STORAGE_KEYS** — каждое поле синхронится отдельно. Для части данных (например, «профиль плана»: manualAssignments + manualLines + assignmentClones) можно ввести один составной ключ и писать один документ вместо трёх — меньше запросов и проще консистентность.
- **subscribeToRemoteState игнорирует fromCache** — при первом открытии показываем данные только после ответа сервера. Можно один раз применить снапшот из кэша для быстрого отображения, затем заменить на серверный.

### 3. Конфликты и ревизии
- **Локальные ревизии** — `rev = Date.now() * 1000 + counter`. При двух вкладках с близким временем возможны пересечения. Надёжнее единый монотонный счётчик (например, в localStorage) или серверные метки времени при записи.
- **applyRemoteSnapshot** при равных rev опирается на pending: не перезаписываем локальные незапушенные изменения. Логика в syncStateApplier и usePlanState сложная; вынести «правило выбора версии» в одну функцию (например, mergeStrategy(key, local, remote, pending)) упростит поддержку.

## Внесённые изменения в коде

1. **Параллельная запись в flushQueue** — ключи пишутся через `Promise.all`, а не по одному.
2. **Один повтор при ошибке** — при падении flushQueue делается одна повторная попытка с задержкой 1.5 с перед вызовом flushErrorCallback.
3. **Один источник правды для pending** — `pendingUpdates`/`pendingMeta` хранятся только в ref (SyncContext); для ре-рендеров при изменении pending используется `pendingVersion` в state. Это убирает массовые ре-рендеры при каждом `persistStateKey`.
4. **Применение remote только при изменении снапшота** — в usePlanState хранится хэш последнего применённого снапшота; при совпадении по содержимому эффект не вызывает applyRemoteSnapshot и не обновляет pending, что устраняет мерцание от «применения своего же облака».
5. **Обновление pending state только при реальном изменении** — `setPendingUpdates`/`setPendingMeta` вызываются только когда содержимое nextPending/nextMeta изменилось (сравнение по JSON), что снижает лишние ре-рендеры.
6. **Пропуск applyPlanData при тех же данных** — в syncStateApplier перед вызовом applyPlanData сравнивается текущий снапшот плана (getCurrentPlanSnapshot) с удалённым; при совпадении applyPlanData не вызывается.
7. **Снижение шума в логе синхронизации** — сообщения о пропуске полей (skip по rev) больше не пишутся в addSyncLogMessage.

Остальные пункты можно внедрять по шагам по мере необходимости.
